# M1.4 review — preserve indexed notes across replacement, failure, and retry

## Outcome and scope

Notes now have stable document IDs, persisted source revisions, and separate index
and summary states. Replacement chunks and validated vectors are built before a
short SQLite transaction swaps the active index and FTS entries. No network calls
run inside that transaction. Failed replacement leaves the old source, chunks,
vectors, and summary intact. Once replacement indexing succeeds, its summary is a
separate retryable stage; the old summary is not attached to the new text.

This is one review unit covering persistence, providers, API, state, Notes UI, and
tests. It completes the M1.4 implementation scope, not M2 retrieval, document reading,
citations, or Loremaster answers. Interactive acceptance remains pending.

## Review focus

- Deduplication checks campaign, filename, content hash, chunker version, and
  embedding model. Completed unchanged uploads make no provider calls. Summary-only
  retry reads the stored source without embedding again.
- A revision is reserved before provider work. Only the latest accepted revision
  can replace the active index; late summaries cannot attach to another revision.
  Concurrent identical jobs share work in one server process. Persisted worker
  leases prevent overlapping processing across connections/processes.
- Vector count, ordering, dimensions, finiteness, nonzero values, and model
  compatibility are checked before commit. Failure receipts and retryable source
  remain available, including after restart.
- Upload outcomes distinguish indexed, unchanged, partial, and failed. The UI
  preserves errors after status refresh, reports interrupted/cancelled work, and
  offers Retry and an explicit per-note Reindex. Provider/model labels and missing
  credentials are visible before upload; Ollama generation does not imply local notes.
- Backfill uses each pending document's own stored source, including older notes
  outside the latest upload batch, scoped to the same campaign.

## Migration and recovery limits

Schema v7 adds revision metadata and source storage without removing legacy chunks
or embeddings. Legacy sources are marked unavailable, never reconstructed from
overlapping chunks. Existing summaries remain; incomplete legacy embedding sets
are identified separately. Reupload only when exact source is needed. New notes
start unindexed even on an upgraded database.

Keep a backup before upgrading. Tests use isolated in-memory/temporary databases;
the user's `notes.sqlite` was not opened or migrated during this implementation.
Do not delete the application database to repair a note.

- Retention: exact text for the current active and latest attempted revision only.
  Older attempts retain metadata/error receipts; their source is dropped after
  supersession. Successful replacement drops the previous active source and index.
  This is recovery for in-flight replacements, not unlimited note history. Deleting
  the note or campaign cascades through its revision records.
- Source text preserves original line endings. Chunk offsets address the
  LF-normalized text used by the chunker; a future reader must use that convention.
- Restart does not automatically resume paid calls. Use Retry; a crashed worker's
  lease expires within six minutes. Stages have a five-minute time budget including
  queue time. A provider may already have charged for interrupted work.
- Cancel/navigation aborts supported provider requests and prevents late index
  commits. Already completed stages remain. Unstarted files have no saved source
  and must be selected again. Identical coalesced requests share the original job's
  cancellation lifetime; another caller can retry afterwards.
- A single embedding model/dimension space remains pinned for the database. Model
  mismatch preserves all existing data: switch back to the indexed model, then
  Retry/Reindex the affected note. Mixed-model migration is not included.
- Reindex rebuilds the selected stored source and may charge for embedding and
  summarization again. Retry resumes missing stages; completed retries are no-ops.

## Resource bounds and API

Uploads accept at most 20 files, 5 MiB per file, 20 MiB total; multipart parsing is
capped at 21 MiB including overhead. At most two batches are admitted and two
provider jobs run concurrently per process. Files are processed sequentially within
a batch, with at most 5,000 chunks per file. Backfill reads one source at a time;
there is no retained full-corpus source map. A busy server returns 429 for retry.

- `GET /api/notes/providers`: public provider/model/configuration labels, never keys.
- `POST /api/campaigns/:id/notes`: bounded multipart upload with per-file SSE outcomes.
- `POST /api/campaigns/:id/notes/retry`: `{ "ids": [1], "reindex": false }`.
  All IDs must belong to the route's campaign; at most 20 are accepted. `true`
  explicitly rebuilds those notes only. Streams include keep-alive comments.
- Existing list responses add active/latest revisions, source availability,
  active/latest index status, and summary status/errors.

Regression coverage includes every replacement failure class, no-op uploads,
summary-only retry, reversed index/summary completion, duplicate coalescing,
cancellation, concurrency limits, provider response validation, backlog source
correctness, campaign ownership, expired leases, legacy migration/reopen, retained
unrelated maps/chats/room notes, foreign-key checks, and rendered UI recovery labels.
Providers are mocked or use local stub servers; no paid cloud calls were made.
Build retains the existing large-bundle warning. Rust was unchanged and not rerun.

The in-app browser could not bootstrap (`sandboxPolicy` missing from sandbox state).
The rendered-markup test is not visual or interactive browser verification. Keep
this PR in draft until these checks have been performed in an isolated test campaign:

1. Check light/dark and narrow layouts, readable long errors, keyboard upload and
   disabled states, provider disclosure, and per-note action labels.
2. Upload twice and observe unchanged. Fail a summary, then use Retry summary;
   verify no second embedding call and accurate searchable/partial status.
3. Start a replacement, cancel/navigate away, and return. Verify the active revision
   survives, stale progress does not follow another campaign, and Retry resumes.
4. Refresh/restart during processing and retry after lease expiry. Verify source
   availability and the distinction between unstarted and saved failed files.
5. Open migrated legacy notes: existing summaries/data remain, missing source and
   incomplete indexes have actionable labels, and only the selected reupload changes.

Use stub providers or explicitly chosen test files/accounts for checks that make
provider calls. Do not use private campaign data as fixtures.
