# M2.1 — revision-bound note reader, hybrid retrieval, and evaluation

## Outcome

The note library now supports reading source revisions and finding passages before
an answering agent is attached. One review unit includes the retrieval service,
reader/API/deep links, source-selection UI, cancellation/ownership state, and the
frozen evaluation corpus. M2.2 Loremaster and M2.3 grounded generation stay separate.

## Implementation and safety

- Keyword search uses FTS5 BM25 over active chunks, scoped to the campaign and
  selected document IDs. Input becomes at most 32 literal OR terms, not raw FTS or
  SQL syntax. It works without credentials or network calls.
- Semantic search embeds the query with the indexed model, validates dimensions
  and values, and scans normalized vectors in the selected campaign. Hybrid uses
  reciprocal-rank fusion (`k=60`, up to 60 candidates per mode), not addition of
  incomparable raw scores. Model/configuration failure is explicit; hybrid falls
  back to keyword results with a visible warning.
- Duplicate candidate IDs and overlapping spans within a document are suppressed.
  Optional one-chunk neighbors expand the returned span only if the full expanded
  context fits. Budget truncation keeps a literal query match where available;
  citations retain exact UTF-16 offsets in LF-normalized source text.
- Ranking, expansion and citation creation share one synchronous SQLite read
  snapshot after the query embedding completes. Replacing a note during the
  provider wait cannot mix its old vectors with a new source revision.
- Source selection is explicit: omitted IDs means all campaign sources; `[]`
  means none, never all. Misowned/missing IDs fail before any provider call.
- The reader checks campaign/document/revision/chunk identity. A superseded source
  returns `410 revision_removed`; a deleted or misowned source returns 404. Links
  never silently follow a filename or redirect to newer text. Legacy sources show
  their stored chunks with an unavailable-original warning.
- Plain source text, including HTML, is escaped by React. Reader pages are capped
  at 20,000 characters, retain Unicode boundaries, and offer heading/passage jumps.
  This is a source inspector, not a rich Markdown editor or an answering agent.
- Search results and filters survive a reader round-trip within the campaign.
  Cancel, changed inputs, leaving search, and campaign navigation invalidate stale
  work. Providers receive cancellation signals; already performed calls may cost
  credit. Keyword mode is the default; semantic modes disclose the provider before
  submission. Scores are rankings, not probabilities or evidence of an answer.

## Diagnostic API

`POST /api/campaigns/:id/notes/search`:

```json
{
  "query": "Vess bronze gate",
  "mode": "hybrid",
  "documentIds": [1, 2],
  "limit": 5,
  "tokenBudget": 3000,
  "neighbors": 1
}
```

Returns passages with campaign/document/revision/chunk/heading/span citations,
per-mode ranks, estimated token counts, warnings, and candidate/model diagnostics.
`mode` defaults to `lexical`. The search service is also callable without HTTP for
future read-only tools; it never changes campaign content.

`GET /api/campaigns/:id/notes/:doc/revisions/:revision?chunk=:chunk` returns the
exact stored source and matching revision chunks. The corresponding browser paths
are `/c/:id/notes/:doc/r/:revision` and `/c/:id/notes/:doc/r/:revision/chunk/:chunk`.

Bounds: 1,000 query characters; 200 explicitly selected sources; 1–20 results;
128–8,000 estimated context tokens. Estimation is `ceil(characters / 4)`, excludes
citation metadata, and is not a model-tokenizer guarantee. At most four concurrent
search requests and two concurrent query-embedding jobs per process are admitted.
Query embedding has a 30-second budget. Semantic scans require at most 50,000 scoped
chunks; larger selections get an actionable warning (hybrid falls back to keywords).
The CPU scan is synchronous, not immediately interruptible, and remains linear.

## Evaluation and verification

```text
bun test                # 1390 passing across 29 files
bun x tsc --noEmit       # passing
bun run build           # passing; existing large-bundle warning remains
bun run eval:retrieval   # target met, no paid calls
git diff --check        # passing
```

The corpus and 90% hybrid hit@5 target were fixed before the first evaluation run;
no relevance labels or thresholds were changed to make it pass. The test pins the
canonical JSON SHA-256. It contains 24 fictional documents, 36 queries (33 answerable),
two campaigns, proper names, paraphrases, multi-source facts, conflicting accounts,
repeated filenames, and missing facts. Results are checked in at
[M2.1-EVAL.json](M2.1-EVAL.json).

| Mode | Hit@5, answerable | All sources@5, multi-source/conflict | Cross-campaign hits |
| --- | --- | --- | --- |
| Keyword | 84.8% (28/33) | 100% | 0 |
| Semantic, synthetic vectors | 100% (33/33) | 100% | 0 |
| Hybrid, synthetic vectors | 100% (33/33) | 100% | 0 |

All modes returned empty results for the three missing/isolation queries in this
fixture. Synthetic word/synonym vectors deliberately make semantic behavior
deterministic; they never read expected IDs. This validates pipeline integration,
**not production embedding quality or a calibrated no-answer decision**. A real
model may rank unrelated material positively. No live cloud queries were made.

Additional regressions cover invalid requests/FTS syntax, empty selections/indexes,
model mismatch, corrupt vectors, fallback, budget/Unicode offsets, neighbors,
late keyword matches, replacement while embedding, cancellation, reader removal,
campaign ownership, hostile source HTML, and stale browser-store results.

## Data and remaining checks

No schema change (still v7), migration, new persistent history, or private-data
fixture. M1.4's source-retention policy remains: active and latest attempted sources
only. Old links explicitly become unavailable after successful replacement or
deletion; this PR does not promise archived citations. Rolling back this code does
not require a database rollback. Keep backups as usual; the user's notes database
was not opened by implementation/evaluation tooling. Rust was unchanged and not rerun.

The browser skill could not connect because the browser tooling failed during setup.
Rendered component tests are not interactive/visual verification. Keep the PR draft
until this walkthrough is checked in an isolated campaign:

1. Upload two fictional notes; open a filename and use heading/passage navigation,
   large-source pagination, browser back/forward, and a pasted/reloaded deep link.
2. Search in Keyword mode with no key; select one source, then none, then all.
   Change context budget and nearby-context setting; follow a result and return.
3. With a stub or explicitly approved test provider, compare Semantic/Hybrid;
   inspect cost disclosure, model mismatch, and visible keyword fallback.
4. Cancel a slow search and switch campaigns. No old results/errors should appear
   in the new campaign. Replace/delete a source and reopen an old link: it must
   report unavailability, not show new text as the cited revision.
5. Verify keyboard labels/focus, long filenames/errors, light/dark themes and narrow
   layouts. The reader renders uploaded HTML as inert text.

The existing M1 interactive checklists remain pending too. No claim is made that
Loremaster answers, generation grounding, export fixes, or usage accounting are done.
