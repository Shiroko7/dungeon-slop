# M2.3 review — grounded Architect, Narrator, and constraint checks

Status: implementation complete on the review branch; browser acceptance is still
pending because the in-app browser bootstrap is unavailable in this environment.

## What changed

- The Architect and Narrator now use the same campaign-scoped hybrid retrieval
  service as the Loremaster. The Architect tab lets the user search all indexed
  notes or choose individual indexed documents, and optionally provide a focused
  retrieval query.
- Retrieval is deliberately bounded: at most 8 ranked passages and a 3,500-token
  retrieval budget are sent to a generation request. Provenance stores the query,
  selected document IDs, revision-bound citations, warnings, and retrieval status.
- Evidence is labelled as untrusted campaign fact in the prompts. The model is
  instructed to distinguish source facts from connective invention rather than
  treating note text as executable instructions.
- Blueprint provenance is persisted with the plan. Room and dungeon descriptions
  persist the provenance used to create them, and the UI links each citation to its
  exact campaign/document/revision/chunk reader route.
- Blueprint edges carry gate and door preferences into the room plan. The map
  report checks planned connections and entrances against the built graph and
  surfaces unmet connections, reachability, room/entrance counts, and unmet
  requirements. Gate and door preferences are explicitly reported as advisory
  until the renderer has a constraint-aware door/lock model.
- The Layout panel exposes an editable room/connection plan. Stable node keys are
  never edited, and users can lock rooms or connections so AI refinement refuses
  changes that would violate those requirements. Plan edits remain proposed until
  the user explicitly generates the map.
- Narrator input derives entries from the actual built room connection graph and
  retains room-ID validation. Existing save, fork, revision, and authored-content
  protections remain in force.

## Refresh and persistence contract

Changing a note does not rewrite an existing plan, map, or description. To use the
new note revision, the user must explicitly run Architect or Narrator again with
the desired source selection. Existing artifacts remain readable and their stored
citations continue to point at the revision that informed them. Failed or cancelled
operations do not silently replace saved content.

room-ID safety, constraint reporting, and existing campaign/save behavior. No live
provider call is required.

## Browser acceptance checklist

1. Open a campaign with at least two indexed notes and a dungeon Architect chat.
2. Select all notes, then select one note, and verify the selection summary and
   optional retrieval-focus field update without losing the chat draft.
3. Generate a config/blueprint. Inspect the campaign-source section and open a
   citation; it must land on the exact source revision and highlighted chunk.
4. Generate the map. Inspect the Layout constraint check for delivered and unmet
   connections/entrances and the explicit advisory gate/door notices.
5. Generate one room and the dungeon overview. Inspect their source sections and
   confirm entries use the actual connected room IDs.
6. Edit or reindex a note. Confirm the existing plan and prose remain unchanged
   until an explicit generation action is run, then verify the new artifact records
   the new revision-bound citations.
7. Exercise cancellation/navigation during retrieval and generation; no response
   from the previous dungeon may appear in the newly opened dungeon.
