# M2.2 review: bounded, citation-backed Loremaster answers

Status: implemented on `milestone-2/loremaster`; draft review. The browser
acceptance checklist remains pending because the in-app browser could not be
bootstrapped in this environment (`sandboxPolicy` was unavailable).

## What this package delivers

The Loremaster can now answer a campaign chat question by researching only that
campaign's notes. The server-side agent has three read-only tools:

- `list_documents` — discover indexed documents and their active revisions;
- `search_notes` — run keyword, semantic, or hybrid retrieval with an explicit
  result count and context budget;
- `read_document` — open a specific document revision/chunk for exact evidence.

Note text is treated as untrusted evidence, not as instructions. Tool arguments
are validated, document ownership is checked, and the agent cannot mutate maps,
notes, chats, or settings.

## Safety and bounded work

- At most 4 agent rounds and 6 tool calls per answer.
- At most 12 evidence passages and bounded tool-result sizes are sent to the
  generation provider.
- Search limits are 1–8 results, a 128–5000 token context budget, and at most
  50 explicitly selected documents.
- Questions are limited to 1–4000 characters.
- The campaign and Loremaster chat are checked on every request; Architect chats
  and cross-campaign document IDs are rejected.
- Cancellation uses an abort signal and leaves the user question plus any
  partial answer visible without saving a misleading assistant response.

## Answer and provenance contract

Answers are streamed over `POST /api/campaigns/:campaignId/chats/:chatId/ask`.
The stream reports user, tool start/result, token, complete, and error events.
Completed assistant messages persist exact source citations (document, revision,
chunk, heading, and snippet) and a bounded record of every read-only tool call.
Citation links open the revision-bound reader route, so later reuploads cannot
silently change what an answer cited.

The prompt requires the model to separate documented facts from uncertainty or
proposed ideas, cite only returned evidence, and say when the notes are
insufficient or contradictory. A malformed or unsupported tool request fails
closed rather than being executed.

## UI/UX

The chat now shows:

- the selected generation provider/model and a cloud-usage disclosure;
- active read-only research activity while a response is running;
- a Cancel answer action;
- streaming text and a clearly labelled cancelled/unsent draft on interruption
  or failure;
- expandable persisted “Research used” provenance;
- source snippets whose links open the exact cited revision and chunk.

## Persistence and migration

The existing `messages.tool_calls` column is reused; no schema migration is
required. Existing chats and messages remain readable, and new assistant
messages carry optional citations and tool-call provenance.

## Verification

Automated coverage includes tool ownership/validation/cancellation, bounded agent
loops and prompt-injection resistance, SSE/API validation, cancellation and
navigation races in the store, chat persistence, citation/provenance rendering,
type checking, and production build. No test uses the committed `notes.sqlite`
database or makes a paid provider call.

Before merging, manually verify in a browser:

1. Ask a question with indexed notes and follow a citation to the exact revision.
2. Confirm tool activity and persisted provenance after reload.
3. Cancel during research and confirm the draft remains visible and no assistant
   message is committed.
4. Try an Architect chat, an empty question, and a second campaign's document;
   each should be rejected without data leakage.
5. Verify cloud provider disclosure and the local Ollama wording match the active
   AI settings.
